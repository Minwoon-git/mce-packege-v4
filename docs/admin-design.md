# MCE Bot 어드민 구조 설계안

> 2026-08-25 미팅 요건 반영 — "고객사별 로그인 + 토큰(사용량) 모니터링·제어 + 온보딩 활성화 구조가 지금 없다"에 대한 설계.
> 결정 대기 항목(과금 방식 등)은 §7에 분리.

## 1. 목표와 범위

- 대상: 크롬 익스텐션(MCE Bot) + web-bridge 서버
- 신규로 만드는 구조 3가지
  1. **인증** — 고객사 계정 단위 로그인 (현행: 화면 텍스트 기반 BU 게이트뿐, 인증 아님)
  2. **사용량 계측·제어** — 계정별 비용 집계, 한도 초과 시 제어
  3. **온보딩 관리** — 고객사 등록 → 세팅 → 활성화를 어드민 화면에서 수행
- 비범위: 가격 정책 결정(§7), SFMC 인증의 계정별 분리(Phase 2 과제)

## 2. 단계별 로드맵

| 단계 | 내용 | 전제 |
|---|---|---|
| **Phase 1 (지금 가능)** | 현행 로컬 web-bridge에 계정·사용량·어드민 최소 구현 | 없음 — 현 구조 위에 증축 |
| **Phase 2 (서버화 후)** | 중앙 서버 멀티테넌트 — 고객사 A/B/C 동시 수용, 계정별 SFMC 인증 분리 | 서버 인프라 확보 (미팅 결정 대기) |

- Phase 1의 데이터 모델·API를 Phase 2에서 그대로 승계하는 것이 설계 원칙 (버리는 코드 최소화)

## 3. 데이터 모델 (Phase 1: 파일 기반 → Phase 2: DB 승계)

**accounts.json** — 고객사 계정 대장
```json
{
  "accounts": [
    {
      "id": "acct_xxxx",
      "name": "어반몰",
      "buName": "Salesforce_milvus_edu",
      "apiKey": "mce_live_...",
      "status": "active",          // pending | active | suspended
      "plan": { "type": "postpaid", "monthlyLimitUsd": 50 },
      "createdAt": "2026-09-01"
    }
  ]
}
```

**usage-YYYYMM.jsonl** — 사용량 원장 (월별 파일, append 전용)
```json
{ "ts": 1756..., "accountId": "acct_xxxx", "chatId": "...", "costUsd": 0.0312, "durationMs": 41200 }
```

- 근거: 서버가 이미 claude 결과 이벤트에서 `total_cost_usd`를 수신 중 (server.js `handleEvent`) — **한 줄 추가로 기록 시작 가능**
- 집계는 조회 시점 계산 (월별 파일이라 스캔 범위 작음). Phase 2에서 SQLite/Postgres로 이관

## 4. 인증 흐름

```
[익스텐션 첫 실행]
  → 로그인 화면 (계정 키 입력: mce_live_...)
  → POST /api/auth  → 서버가 accounts.json 대조 → { name, status } 반환
  → chrome.storage.local 저장 (이후 자동 로그인)

[이후 모든 요청]
  → /api/chat 등에 Authorization: Bearer <apiKey> 헤더
  → 서버: 키 검증 → status=active 확인 → 사용량 한도 확인 → 통과 시 실행
  → 실패 시 401/402/403 + 사유 → 익스텐션이 안내 화면 표시
```

- **키 발급·회수는 어드민에서만** (아래 §6). 키 노출 시 어드민에서 재발급
- 현행 BU 게이트(allowedAccounts, 화면 텍스트 검색)는 "어느 BU 화면에서 버튼을 보여줄지"용으로 **보조 유지** — 인증을 대체하지 않음
- 사이드바 하단·설정에 로그인된 계정명 표시, 로그아웃 제공

## 5. 사용량 계측·제어

- **계측**: 매 응답의 `total_cost_usd`를 accountId에 귀속해 원장 기록 (§3)
- **집계 API**: `GET /api/admin/usage?month=2026-09` → 계정별 합계·건수·평균
- **제어(한도)**
  - soft limit (예: 한도 80%) → 응답 말미에 안내 문구 부착
  - hard limit (100%) → `/api/chat` 402 반환, 익스텐션은 "이번 달 한도 소진 — 관리자 문의" 화면
  - 한도 값은 계정별 plan에 저장, 어드민에서 수정
- **과금 계산은 별도** — 원장(원가 USD) × 정책(마진 %, 크레딧 차감 등)은 §7 결정 후 부착. 원장을 먼저 쌓는 것이 핵심 (정책이 늦게 정해져도 소급 계산 가능)

## 6. 온보딩 관리 (어드민 화면)

- 위치: web-bridge 내장 `GET /admin` (관리자 비밀번호로 보호 — env `ADMIN_PASSWORD`)
- 흐름: **등록 → 세팅 → 활성화** (미팅에서 나온 구조 그대로)
  1. 등록: 고객사명·BU명 입력 → 계정 생성 (status: pending)
  2. 세팅: API 키 발급, plan(한도) 설정, (Phase 2) SFMC 인증 연결
  3. 활성화: 확인 버튼 → status: active → 그 순간부터 익스텐션 로그인 가능
- 화면 구성
  - **계정 목록**: 이름 · 상태 · 이번 달 사용량/한도 · 마지막 사용일
  - **계정 상세**: 키 재발급 / 일시정지(suspended) / 한도 수정 / 월별 사용량 추이 (챗봇 대시보드의 차트 컴포넌트 재사용)
  - **온보딩 위저드**: 등록→세팅→활성화 3단계
- 어드민은 **우리(운영자) 전용** — 고객사 마케터에게는 노출하지 않음 (고객사용 "설정"은 챗봇 사이드바에 추후 별도)

## 7. 결정 대기 / 선결 과제

- **과금 방식** — 선불 크레딧 차감 vs 후불 청구, API 원가 + N% (미팅에서 부장님 결정 사항)
- **서버화 시점** — Phase 2 전환 조건 (중앙 배포 없이는 고객사별 설치형으로 Phase 1 반복)
- **계정별 SFMC 인증 분리** — 현재 브릿지 PC의 claude 인증 1개를 전 계정이 공유. 멀티테넌트의 실질 난제 (MCP 인증을 계정별 프로파일로 분리하거나 계정별 브릿지 인스턴스)
- **키 전송 보안** — Phase 1 로컬(localhost)은 무관, Phase 2 중앙 서버는 HTTPS 필수

## 8. Phase 1 구현 규모 (참고)

- 서버: accounts 로드/검증 미들웨어 + 사용량 기록 1줄 + admin 라우트/화면 — **2~4일**
- 익스텐션: 로그인 화면 + Authorization 헤더 + 한도 안내 화면 — **1~2일**
- 어드민 화면: 목록·상세·위저드 (대시보드 컴포넌트 재사용) — **2~3일**
