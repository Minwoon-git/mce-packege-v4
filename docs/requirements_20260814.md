## 🚧 1순위 작업 — 단계 분할

한 덩어리로 잡으면 재플랫폼 규모가 됨(테넌트별 SFMC 인증 + 권한 샌드박스 + 상태 외부화 + Windows 종속 제거 동시 발생). 3단계로 분할.

| 단계 | 범위 | 목적 |
|---|---|---|
| **Phase 0** | ① SFMC 인증의 헤드리스 성립 여부 → **✅ 완료(하단 검증 결과)** ② OAuth 동의 플로우 헤드리스 완주 확인 ③ 리눅스 컨테이너에서 워크플로 스모크 테스트 ④ 테스트 계정 BU 2개로 테넌트 A/B 확인 ⑤ 자체 라이선스/결제 방식 결정 | 최소 비용으로 성립 여부 확인 |
| **Phase 1** | 단일 테넌트 원격 실행 — 자사 서버에서 1개 BU 기준 동작, 확장의 `localhost:3456` → 서버 도메인 교체 | "로컬 종속 제거"를 최저 위험으로 달성. 데모·영업 가능 상태 |
| **Phase 2** | 멀티테넌트 + 권한 샌드박스 + 사용량 계측 → 웹스토어 배포·구독 | 상용화 |

### Phase 1에서 실제로 바뀌는 것

- `web-bridge/server.js` — Windows 종속 제거(`shell:true` 스폰, `taskkill /T /F`), `.cmd`/`.vbs` 자동시작 스크립트 폐기
- `chrome-extension/manifest.json` — `host_permissions` 를 `localhost:3456` → 서버 도메인, CORS 오리진 정리
- 서버 측 Claude 실행 환경 + 자사 엔터프라이즈 API 키
- SFMC MCP 인증 토큰의 서버 보관·갱신

### Phase 2로 미루는 것

- 인메모리 상태(`running`/`lastResult` Map) 외부화 — 단일 인스턴스면 Phase 1에서는 유지 가능
- `--dangerously-skip-permissions` → 도구 allowlist 전환 — **외부 공개 전 필수**
- 산출물 오브젝트 스토리지 이관, 테넌트별 워크스페이스 격리

## 🔬 검증 결과 — SFMC 인증 (2026-08-20)

**Test A: 서버가 사람 없이 SFMC 토큰을 갱신할 수 있는가 → ✅ 가능 (갈래 A 확정)**

| 확인 항목 | 결과 | 근거 |
|---|---|---|
| `sf-mce-mcp` 연결 형태 | HTTP 원격 MCP, 정상 연결 | `claude mcp list` |
| 인증 주체 | **MC 사용자(사람) 단위 OAuth** — 패키지 단위 서버 인증 아님 | 사용자별 라이선스 필요, 미부여 시 `user_not_licensed` |
| **refresh 토큰** | **존재** | 로컬 인증 정보 확인(사용자 확인) |
| 재인증 빈도 | 서버 이름 변경 등 이벤트 시에만 1회 | 운영 경험 |

**→ 결론**: 온보딩 시 고객 MC 사용자가 **브라우저로 1회 동의** → refresh 토큰을 서버가 보관·갱신 → 이후 **헤드리스로 지속 사용**. 즉 `client_credentials` 기반 **자체 MCP/도구 계층 구축이 Phase 1 범위에서 제외**됨 (작업량 대폭 감소). Test B는 보류.

**설계 원칙 (확정)**: 토큰을 PC에서 서버로 복사하지 않고, **OAuth 동의 플로우 자체를 서버에서 개시**한다. 고객은 우리 서버가 제시한 URL로 MC 로그인·동의만 하고, refresh 토큰은 처음부터 서버에 저장된다. (device binding 문제 자체가 발생하지 않음)
