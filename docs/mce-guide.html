Marketing Cloud Engagement 소개

Marketing Cloud Engagement(MCE, 구 ExactTarget)는 Salesforce의 B2C 마케팅 자동화 솔루션

고객 데이터를 한곳에 모아 세그먼트를 만들고, 이메일·SMS·푸시·카카오 등 다채널 메시지를 고객 여정(Journey)에 따라 자동 발송하는 플랫폼.

플랫폼 핵심 기능

  • 데이터 통합 — 고객 마스터·구매 이력·행동 데이터를 Data Extension(테이블)으로 적재·관리
  • 세그먼테이션 — SQL·필터로 타겟 고객군 추출 (예: 90일 미구매 이탈위험군)
  • 캠페인 실행 — Journey Builder로 진입 → 발송 → 대기 → 분기 흐름을 설계해 자동 실행
  • 다채널 발송 — 이메일 · SMS · 푸시 · (커스텀 액티비티 연동 시) 알림톡/카카오
  • 성과 추적 — 발송·오픈·클릭·반송 데이터를 Data View로 축적, 후속 캠페인에 재활용

계정 구조 — Business Unit

하나의 MCE 계정(테넌트)은 여러 Business Unit(BU)으로 나뉨. BU는 브랜드·법인·조직별 독립 작업 공간으로, 데이터·콘텐츠·발신 설정·구독자가 BU 단위로 분리.

MCE 계정 (테넌트 — 28자 Subdomain으로 식별)
 ├─ BU A (브랜드 A)  ── DE · Journey · 이메일 · 발신 프로필
 ├─ BU B (브랜드 B)  ── 독립된 데이터·콘텐츠·설정
 └─ BU C (테스트)    ── 커스텀 액티비티·키 값도 BU마다 다름
Note같은 계정이라도 로그인 사용자에게 BU 접근 권한이 없으면 그 BU의 데이터를 볼 수 없음. API 연동(Installed Package) 권한도 BU 단위로 동작.

데이터 구조

Contact와 Subscriber

  • Contact — 채널 무관 "한 사람". Contact Key로 식별되며 이메일·SMS·푸시 주소가 모두 이 아래에 연결
  • Subscriber — 이메일 채널 관점의 수신자. Subscriber Key로 식별 (일반적으로 Contact Key와 동일 값 사용 권장)
  • All Contacts / All Subscribers — 계정 전체의 연락처·구독자 마스터 목록

Data Extension (DE)

MCE의 데이터 테이블. 관계형 DB의 테이블처럼 컬럼(필드)·기본키·데이터 타입을 갖고, 고객 마스터·구매 이력·세그먼트·발송 대상까지 모든 데이터가 DE에 저장.

  • Sendable DE — 발송 대상으로 쓸 수 있는 DE. Subscriber Key와 연결(Send Relationship) 필수
  • Filtered DE — 조건 필터로 만든 부분집합 DE
  • 적재 방법 — Import(SFTP/CSV) · SQL Query 결과 · API upsert · 수동 업로드

Data View — 발송 결과 테이블

발송·반응 로그가 자동으로 쌓이는 시스템 테이블. UI에는 보이지 않고 SQL Query로만 조회 가능.

Data View내용
_Sent발송 완료 로그
_Open이메일 오픈 로그
_Click링크 클릭 로그
_Bounce반송(하드/소프트 바운스) 로그
_Unsubscribe 등수신거부·구독 상태 변경 로그
NoteData View 보존 기간은 기본 6개월. 장기 분석을 하려면 주기적으로 별도 DE에 적재(백업)하는 파이프라인 구성이 필요.

Contact Builder

DE 간 관계(Attribute Group)와 Contact 중심 데이터 모델을 설계하는 도구. Journey의 Decision Split에서 진입 DE 밖의 속성을 참조할 때 이 모델을 사용.

스튜디오 & 빌더

Builder

Journey Builder

고객 여정을 캔버스에 설계·자동 실행하는 핵심 모듈. 진입 → 발송 → 대기 → 분기 → 종료 흐름 구성. (다음 장에서 상세)

Builder

Content Builder

이메일·템플릿·이미지·코드 스니펫 등 발송 콘텐츠의 통합 저장소. 폴더 구조로 에셋 관리, 개인화 문법(AMPscript·Personalization String) 지원.

Studio

Email Studio

이메일 채널 관리 — 구독자 리스트, 발신 프로필(Sender Profile), 발송 분류(Send Classification), A/B 테스트, 수동 발송.

Studio

Automation Studio

배치 자동화 도구. SQL Query · Import · File Transfer · Script 액티비티를 스케줄(매일 새벽 등)로 예약 실행. 데이터 파이프라인의 중심.

Studio

Mobile Studio

모바일 채널 3종 — MobileConnect(SMS/MMS), MobilePush(앱 푸시·지오펜스), GroupConnect(LINE·Facebook Messenger). 국내 알림톡/카카오는 기본 제공이 아니라 커스텀 액티비티(벤더 연동)로 처리.

Builder

Analytics Builder

발송 성과 리포트·트래킹. 심화 분석은 Data View를 SQL로 집계하거나 Intelligence 제품 연계.

캠페인 제작 5단계

  1. 데이터 준비 — Automation Studio에서 SQL/Import로 타겟 세그먼트 DE 생성
  2. 콘텐츠 제작 — Content Builder에서 이메일·템플릿 제작
  3. 여정 설계 — Journey Builder에서 진입 소스(DE) + 액티비티 흐름 구성
  4. 발송 설정 — Sender Profile·Send Classification 지정
  5. 발행·모니터링 — Journey 발행 후 Data View로 성과 추적

Sender Authentication Package (SAP)

발신 도메인·IP를 우리 브랜드 소유로 인증하는 패키지. 미구성 시 공유 도메인/IP로 발송되어 스팸 분류 위험이 커짐. 구성 요소는 4가지.

구성역할
Private Domain발신(From) 도메인 — SPF·Sender ID·DKIM으로 "우리가 보낸 메일"임을 수신 서버에 증명
Dedicated IP우리 계정 전용 발송 IP — 평판을 직접 관리 (대략 월 10만 통 이상 발송 시 권장)
Account Branding링크 트래킹·이미지·웹페이지 보기 URL을 공유 도메인 대신 우리 도메인으로 래핑
Reply Mail Management구독자 회신 메일 처리 (자동응답·수신거부 키워드 감지 등)

IP 워밍

새 전용 IP는 발송 평판이 없어, 처음부터 대량 발송하면 스팸으로 차단됨. 소량부터 점진적으로 발송량을 늘려 평판을 쌓는 과정이 IP 워밍.

  1. 가장 반응 좋은(최근 오픈·클릭) 구독자부터 소량 발송 시작
  2. 일자별 램프 스케줄로 단계적 확대 — 주당 15~20% 증량 권장, 발송량 2배 증량은 최소 2주 간격
  3. 반송률·스팸 신고율·오픈율 모니터링, 이상 시 램프 속도 조절
  4. 목표 물량 도달까지 통상 4~6주

수신 동의 관리

  • 구독 상태 — Subscriber 단위 Active/Unsubscribed, 이메일·SMS 채널별 동의 별도 관리
  • 법적 요건 — 상업 메일에 수신거부 링크·회사 물리 주소 필수 (정보통신망법·CAN-SPAM)
  • 발송 대상 필터 — 세그먼트 조건에 채널 동의 필터를 교집합으로 적용해야 실제 발송 가능 인원이 됨

Installed Package — API 연동의 관문

Administration → Installed Packages에서 API Integration 컴포넌트를 만들고 권한(Scope)을 부여. OAuth 2.0 기반이며 유형은 3가지.

유형인증 (OAuth 2.0)용도
Server-to-ServerClient Credentials — 사용자 개입 없음서버 간 백그라운드 연동 (배치·시스템 통합)
Web AppAuthorization Code — 사용자 로그인, Secret을 서버에 안전 보관서버가 있는 웹 애플리케이션
Public AppAuthorization Code — 사용자 로그인, Secret 보관 불가 환경SPA·모바일 앱 등 Secret을 숨길 수 없는 클라이언트

Web/Public App은 사용자를 대신해 동작하므로 실제 권한 = 앱 Scope ∩ 로그인 사용자 권한.

Note테넌트 ID(28자 Subdomain)와 패키지 Client ID(24자)가 API 엔드포인트를 구성하는 두 열쇠. Authentication Base URI에서 확인.

커스텀 액티비티 — Journey Builder 확장

Journey Builder 캔버스에 기본 제공되지 않는 기능을 액티비티 형태로 끼워 넣는 공식 확장 방식. 개발사가 Installed Package의 Journey Builder Activity 컴포넌트로 등록하면, 마케터는 이메일·SMS 액티비티와 동일하게 캔버스에 드래그해 사용.

동작 구조

  1. 등록 — Installed Package에 Journey Builder Activity 컴포넌트를 추가하고 벤더 서버의 엔드포인트 URL 지정. 설치된 BU의 캔버스 팔레트에 아이콘으로 표시
  2. 설정 — 마케터가 캔버스에서 액티비티를 열면 벤더가 호스팅하는 설정 화면(iframe)이 표시. 선택한 값(템플릿·발신 채널 등)이 액티비티의 inArguments로 저장
  3. 실행 — 저니를 흐르는 고객이 액티비티에 도달할 때마다 Journey Builder가 벤더 서버의 execute 엔드포인트를 REST로 호출. 요청은 JWT로 서명되어 벤더 측에서 위조 검증 가능
  4. 데이터 전달 — inArguments에 {{Event.<이벤트키>.<필드>}} 표기로 진입 DE의 필드를 바인딩하면, 실행 시점에 해당 고객의 실제 값으로 치환되어 전달 (이름·전화번호 등 개인화 변수)

AMPscript

이메일·CloudPages·SMS 본문에 %%[ ... ]%% 블록으로 삽입하는 MCE 고유 언어. 발송 시점에 수신자별로 실행됨.

%%[
  VAR @grade, @coupon
  SET @grade = AttributeValue("Grade")
  IF @grade == "VIP" THEN
    SET @coupon = Lookup("Coupon_DE", "Code", "Grade", "VIP")
  ENDIF
]%%
안녕하세요 %%FirstName%%님, 쿠폰 코드: %%=v(@coupon)=%%
  • 주요 기능 — 조건 분기(IF/ELSE), 다른 DE 조회(Lookup·LookupRows), 날짜/문자열 함수, 개인화 URL 생성
  • SSJS(Server-Side JavaScript) — AMPscript보다 프로그래밍 친화적. 이메일보다는 CloudPages·Automation Script 액티비티에 적합
ImportantAMPscript 오류(존재하지 않는 필드 참조 등)는 해당 수신자의 발송 실패로 이어짐. 발송 전 Preview & Test로 여러 수신자 케이스를 반드시 확인.

SQL Query 작성 시 유의사항

CRM 연동 (Marketing Cloud Connect)

연동 범위

  1. 데이터 동기화 (Synchronized Data Sources) — CRM의 Contact·Lead·Campaign·커스텀 오브젝트를 주기적(최소 15분)으로 MCE의 Synchronized DE로 복제. 읽기 전용이며 SQL로 가공해 발송 DE 생성
  2. 저니 진입 연동 — Salesforce Data 진입 소스: CRM 레코드 생성·변경(예: Case 종료, 기회 성사)을 감지해 저니 진입
  3. CRM 액티비티 — 저니 안에서 CRM 레코드 생성/수정 (Task 생성, 캠페인 멤버 추가 등)
  4. 발송 이력 기록 — 이메일 발송·오픈·클릭이 CRM의 Contact/Lead 레코드에 표시 — 영업 담당자가 마케팅 접점을 확인 가능
  5. CRM 대상 발송 — CRM의 캠페인·리포트를 그대로 발송 대상으로 지정 가능

설계 시 핵심 결정

  • Subscriber Key 전략 — CRM 연동 시 Subscriber Key = CRM Contact/Lead ID(18자) 사용이 표준. 이메일 주소를 키로 쓰면 동일인 중복·주소 변경 문제 발생
  • 동기화 범위 — 필요한 오브젝트·필드만 동기화 (전부 켜면 데이터량·동기화 지연 증가)
  • BU 매핑 — CRM 조직 ↔ MCE BU 연결 구성은 초기 설치 시 결정
NoteMC Connect는 CRM 측 관리 패키지(managed package) 설치 + 양쪽 계정 연결 작업이 필요한 구축 항목 — 사용 중인 CRM이 없다면 이 장은 건너뛰어도 무방.

Marketing Cloud Personalization 소개

Marketing Cloud Personalization(MCP)은 웹사이트·앱 방문 고객을 실시간으로 개인화하는 솔루션

방문 중 발생하는 행동(페이지뷰·클릭·검색 등)을 실시간으로 수집하고, 방문자에게 가장 적합한 콘텐츠·상품·오퍼를 골라 노출하는 플랫폼.

Note — 이름이 비슷한 별도 제품Salesforce Personalization(구 Einstein Personalization)은 Data 360 기반으로 새로 만든 차세대 개인화 제품으로, 이 장에서 다루는 MCP와는 별개. 둘 다 현재 지원되며 MCP 고객은 MCP+ SKU로 Salesforce Personalization도 이용 가능.

Engagement와의 차이

둘 다 "고객에게 맞는 메시지"를 다루지만 방향이 반대.

구분Engagement (MCE)Personalization (MCP)

채널이메일 · SMS · 푸시 · 알림톡웹사이트 · 모바일 앱 · (API로) 콜센터·매장
타이밍스케줄·트리거 기반 발송접속한 그 순간 실시간 반응
단위세그먼트 (수천~수만 명)개인 1명 (1:1 개인화)
예시"이탈위험 고객 2,528명에게 쿠폰 메일""지금 등산화만 3번 본 방문자에게 등산화 기획전 배너"
Note둘은 경쟁이 아니라 보완 관계 — MCP가 포착한 실시간 행동(관심 카테고리·이탈 징후)을 MCE 캠페인의 트리거·세그먼트로 넘겨 "웹에서 본 상품을 이메일로 리마인드"하는 식으로 연계.

주요 기능

  • 웹 개인화 — 방문자 관심사에 맞는 배너·상품 추천·팝업을 실시간 교체
  • 행동 추적 — 페이지뷰·클릭·체류시간·장바구니 행동을 익명 단계부터 수집
  • 친화도(Affinity) 프로파일 — "이 고객은 아웃도어 70%·러닝 30% 관심" 같은 성향 자동 산출
  • AI 추천·의사결정 — Einstein Recipes(상품/콘텐츠 추천)·Einstein Decisions(Next-Best-Offer)
  • 실시간 트리거 — 이탈 징후·가격 하락·재입고 등 이벤트를 잡아 MCE 발송으로 연결
  • A/B 테스트 — 개인화 적용군 vs 미적용군(Control) 성과 비교

실시간 개인화 동작 방식

처리 흐름

  1. 추적 (Beacon) — 웹사이트에 심은 JavaScript beacon(또는 모바일 SDK)이 페이지뷰·클릭·검색어·장바구니 행동을 수집. Sitemap 설정으로 "이 페이지는 상품 상세, 카테고리는 신발" 같은 의미를 부여
  2. 통합 프로필 (Unified Profile) — 익명 방문자도 쿠키 기반으로 추적하다가 로그인·이메일 클릭 시 기존 고객 프로필과 병합. 행동 이력 + 속성 + 친화도가 한 프로필에 축적
  3. 결정 (Einstein) — 캠페인 규칙 + AI가 개인별 노출 콘텐츠를 실시간 결정
    • Einstein Recipes — 협업 필터링·유사도 기반 상품/콘텐츠 추천
    • Einstein Decisions — 여러 오퍼 중 전환 확률이 가장 높은 것 자동 선택
  4. 노출 (Campaign) — 결정된 콘텐츠를 채널에 반영

MCE와의 연계

사용 흐름 — 수동 모드 기준

사용자 관점에서 실제로 오가는 대화 흐름. CLI·Slack 봇·Chrome 확장 어디서든 동일하게 동작.

단계사용자가 하는 일에이전트가 하는 일
1. 요청캠페인 의도를 한 문장으로 입력 (예: "이탈 고객 캠페인 만들어줘")고객 데이터를 진단해 캠페인 후보 표(세그먼트·인원·비율) 제시
2. 선택후보 표에서 캠페인 지정 (번호 또는 "추천대로")실행 모드(수동/자동) 질문
3. 합의수동 선택 시 — Plan(대상·채널·분기·발송 스케줄)을 보고 승인 또는 수정 요청합의된 Plan으로 xlsx 정의서 생성
4. 대기없음 (자동 진행)정의서 기반으로 이메일 에셋 → Event Definition → Journey 생성 (Draft)
5. 결과 확인결과 보고(표 + 저니 흐름도 + Journey 링크) 확인생성 이력 기록
6. 발행Journey Builder UI에서 Draft 검토 후 직접 발행— (발행은 사람이 결정)
  • 자동 모드 — 2단계에서 자동을 선택하면 이후 질문 없이 STEP 1~4를 일괄 실행하고 맨 마지막 결과만 1회 보고
  • 정의서 첨부 — xlsx/CSV/Google Sheets를 직접 첨부하면 1~3단계를 건너뛰고 4단계(Journey 생성)로 직행
  • 리스트업 — 의도 없이 "생성 가능한 캠페인 리스트 업"을 입력하면 진단표 + 추천 목록 + 분석 리포트(PPT)를 받고, 이후 캠페인을 지목하면 위 2단계부터 이어짐
  • 과정 비노출 — 진행 중간 설명 없이 질문·최종 결과·오류만 표시 (결과만 전달 원칙)

신규 고객사 온보딩 (STEP 0)

새 고객사는 캠페인 생성 전에 데이터 인입 세팅을 1회 수행.

  1. 스키마 파일(DDL/CSV) 분석 → 표준 컬럼 매핑·조인키 도출
  2. 핵심 정의 확정 — 고객 ID · 총구매액 산식 · 취소/환불 제외 · 동의값 해석
  3. 빈 RAW DE 생성 + SFTP Import 세팅 + 고객사 분석 가이드 자동 생성
  4. 고객 SFTP 업로드로 데이터 적재 완료 후 STEP 1 진행 가능
Note발송(진입) DE에는 채널 동의 필터가 적용됨 — 실제 발송 인원 = 세그먼트 ∩ 동의. 저니·DE 조회 요청은 항상 실시간 SFMC를 바라봄.
알림톡/문자 캠페인메시지 채널이 알림톡/카카오/SMS면 micrm 모바일 컨텐츠 seq를 먼저 확보해 정의서에 기록. 저니에 넣는 값은 모바일 컨텐츠 seq이며 알림톡 템플릿 id가 아님 (혼동 시 "사용할 수 없는 콘텐츠" 오류).

브랜드 킷 기반 이메일 생성

캠페인마다 이메일을 처음부터 만들지 않고, 고정 틀 + 브랜드 킷 + 본문 생성의 3층 조합으로 초안을 자동 생성해 Content Builder에 등록(emailId 반환) → 저니에서 사용.

발송 인프라 상태를 실시간 점검해 구성됨 / 점검필요 / 수동확인으로 분류. 계정 설정을 변경하지 않음.

  3. IP 워밍용 Journey — 워밍 대상 DE + 램프 단계별 Decision Split 저니 (Draft)

데이터 분석

패키지의 캠페인 추천은 "필드가 있으니 이 캠페인 가능" 수준이 아니라, 실데이터 집계·분포 진단에 기반. 분석·집계는 전부 SFMC 안(DE + SQL + Automation)에서 처리되고, AI는 집계 결과만 읽어 판단.

단계별 상세

  1. RAW 적재 — 고객사가 SFTP로 업로드한 파일을 Import Automation이 RAW DE(고객·구매마스터·구매상세·제품·쿠폰 등)로 적재
  2. 프로파일 빌드 — 여러 RAW 테이블을 SQL로 JOIN·집계해 고객 1명 = 1행의 프로파일 DE를 생성. 총구매액 산식·취소/환불 제외·동의값 해석은 온보딩(STEP 0)에서 확정한 규칙을 적용. 원천이 단일 평탄화 DE면 이 단계는 생략
  3. 세그먼트 사전 집계 — 분석 가이드 정의에 따라 세그먼트별 카운트 DE(SEG_*)를 만드는 SQL을 새벽 Automation으로 실행. "세그먼트 인원 = 카운트 DE의 행 수"로 인코딩해 두는 것이 핵심
  4. 진단·추천 — AI는 raw 데이터를 직접 스캔하지 않고 각 SEG_* DE의 rowCount(메타)만 읽어 분포를 파악. 두드러진 세그먼트에서 추천 캠페인과 기준선을 스스로 도출
  5. 진입(타겟) DE 생성 — 캠페인 확정 후, 세그먼트 조건에 채널 동의 필터(이메일·SMS 동의)를 교집합으로 적용한 발송 대상 DE를 Automation으로 생성·갱신. 실제 발송 인원은 진단 인원보다 작아짐
  6. Journey 진입 — 진입 DE를 Entry Source로 연결하고 스케줄(1회/반복)로 고객이 저니에 진입 → 발송. 결과는 Data View로 회귀해 다음 진단의 재료가 됨

진단 방법 — 프로파일링 기반 자율 도출

추천할 캠페인 목록과 기준선을 문서에 미리 정해두지 않음. AI가 프로파일 DE의 신호 컬럼(구매 횟수·최근 구매일·로그인일·등급·생일 등)을 프로파일링(분포 집계)해 두드러진 지점을 찾고, 거기서 캠페인과 기준선을 도출.

고객 데이터 분석 (모수 10,000명)
지표                  | 인원   | 비율 | 추천 캠페인
1회성 구매자          | 6,400 | 64% | 2차 구매 유도
휴면 (로그인 90일+)   | 3,500 | 35% | 휴면 고객 재활성화
이탈위험 (주문 90일+) | 2,528 | 32% | 이탈 고객 재구매 유도
  • 기준선 자율 결정 — "휴면 = 90일"처럼 고정 임계값을 쓰는 경우 "이 기준으로 가정함"을 결과에 명시
  • 추천 순서 — 비율(모수 대비 규모)이 큰 세그먼트 순으로 우선순위 제시
  • 의도 대응 — 사용자가 의도를 말하면(예: "장바구니 캠페인") 해당 신호의 상세 후보 표로, 의도가 없으면(리스트업) 전체 진단표로 응답

진단 인프라 부트스트랩과 재집계

  • 부트스트랩 — 진단에 필요한 SEG_* 카운트 DE·SQL·Automation이 계정에 없으면 AI가 분석 가이드 정의로부터 직접 생성해 적재. 다중 테이블 원천이면 프로파일 빌드(JOIN 집계)까지 포함
  • 낡음 감지 → 자동 재집계 — Automation이 멈춰 있거나 마스터 DE가 변경돼 집계가 낡았으면 재집계 후 진단
  • rowCount만 읽는 이유 — 즉석 집계(추천 때마다 SQL 실행)는 매번 1~2분 대기가 생기고 비동기 특성상 0건 오판 위험이 있어, 새벽 사전 집계분의 행 수(메타)만 읽는 방식으로 설계. raw 스캔이 없어 개인 데이터가 대화로 노출되지 않는 부수 효과도 있음

설계 원칙

  • 사전 집계 + rowCount 진단 — 무거운 집계는 서버(Automation)가 새벽에 처리하고, AI는 건수만 읽음
  • 다중 테이블 자동 통합 — 정규화된 여러 테이블을 AI가 스키마를 읽고 JOIN·집계해 프로파일로 통합
  • 캠페인 목록 하드코딩 금지 — 추천 캠페인·기준선은 세그먼트 분포에서 AI가 직접 도출
  • 오류 자가 학습 — 생성 중 오류를 수정/우회하면 원인·해결책을 error-log에 기록해 반복 방지

분석 가이드 2층 체계

AI가 고객 데이터를 올바로 해석하게 하는 "데이터 의미 사전 + 분석 방법" 구조. 새 고객사 추가 시 고객사 파일 1개만 늘리면 됨.

층파일내용
공통 방법 (모든 고객사 동일)_common.md프로파일링 → 캠페인 자율 도출 방법, 사전 집계 절차, 다중 테이블 JOIN 표준, 진단 인프라 부트스트랩
고객사 값 (고객사마다 변경)<고객사>.md스키마·의미 규칙(거래금액 세금 전/후, 포인트 포함 여부), 동의·상태 컬럼 매핑, 채널·발송 고정값(GUID·알림톡 키)
NoteMD는 "의미 사전"이지 쿼리·캠페인 카탈로그가 아님 — 캠페인 목록·기준선·측정 세그먼트는 AI가 데이터를 보고 정함.

분석 리포트

리스트업/진단 직후 진단 결과를 문서형 분석 리포트(PPT)로 자동 생성해 파일로 제공. 공통 리포트 템플릿·품질 가이드를 따르고, 값은 해당 고객사 진단·분석 가이드 기준으로 채움.

보안 관리

패키지가 인증·권한·데이터·비밀값을 다루는 방식. 핵심은 자격증명을 로컬에 두지 않고, 데이터 처리는 SFMC 안에서 끝내고, 쓰기 작업은 사람이 통제하는 구조.

인증 — 사용자 OAuth

  • Public App OAuth — 개인 SFMC 계정으로 브라우저 로그인 1회. Client Secret을 로컬에 입력·보관하는 과정이 없음
  • 토큰 관리 — OAuth 토큰은 각 PC의 로컬 자격증명 파일에만 저장(깃 미추적). 만료 시 /mcp 재인증으로 갱신, PC를 옮기면 새로 인증
  • 행위 주체 = 로그인 사용자 — 모든 API 호출이 로그인한 개인 계정 명의로 실행되어 SFMC 감사 로그에 그 사용자로 기록

권한 통제 — 3중 게이트

게이트통제 내용관리 위치

② 패키지 라이선스Installed Package 사용자별 라이선스 — 없으면 인증 자체가 거부(user_not_licensed)Administration → Installed Packages

데이터 보호

  • 집계는 SFMC 내부에서 — 프로파일 빌드·세그먼트 집계가 전부 SFMC 안의 SQL·Automation으로 실행. 고객 원본 데이터가 외부로 반출되지 않음
  • AI는 rowCount(메타)만 읽음 — 진단 시 raw 행을 스캔하지 않아 개인정보가 대화 컨텍스트로 노출되지 않는 구조
  • 원격 MCP — MCP 서버는 Salesforce가 호스팅. API 호출이 Salesforce 인프라 안에서 처리되고, 로컬에 서버·자격증명 저장소를 두지 않음

쓰기 작업 통제

  • 조회는 읽기 전용 — 저니/DE/이메일 목록 등 조회 요청은 실시간 읽기만 수행
  • 저니는 Draft로 생성 — 발행(실제 발송 시작)은 사람이 Journey Builder UI에서 검토 후 직접 결정
  • 기본 세팅은 승인 후 실행 — 계정에 객체를 생성하는 작업은 생성 예정 목록을 제시하고 승인 1회를 받은 뒤 실행. 기존 객체는 삭제/덮어쓰지 않는 멱등 설계
  • 온보딩 점검은 읽기 전용 — 계정 설정을 변경하지 않고 상태 분류만 수행

감사 추적

  • SFMC Audit Trail — 계정 내 변경·접근이 SFMC 감사 로그에 기록되고, 기본 세팅의 감사로그 적재를 켜면 DE로 상시 축적·조회 가능
  • 생성 이력 — 패키지가 만든 저니는 로컬 이력 파일에 누적 기록되어 언제 무엇을 만들었는지 추적 가능
